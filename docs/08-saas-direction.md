# 08 — تغيير الاتجاه: متجر + أفلييت كخدمة SaaS لعدة تجار

**القرار (ADR-008):** المنتج يُباع كخدمة لعدة تجار، كل تاجر له متجره وبرنامج أفلييت خاص به. هذا يلغي خيار البناء على 6Valley، ويغيّر جزءًا من الوثائق 01–07 (التفاصيل في §5).

## 1. لماذا لا 6Valley

- ترخيص CodeCanyon المعتاد يسمح بنطاق واحد لكل ترخيص، وبحسب مدونة 6amTech نفسها فإن الترخيص العادي لا يسمح بتحصيل رسوم من المستخدمين النهائيين، ويحتاج ذلك الترخيص الموسع (Extended).
- حتى الموسع يبقى لنطاق واحد، ولا يناسب بالضرورة تشغيل عدة تجار في نظام واحد. (المصدر تسويقي من 6amTech؛ لم أقرأ شروط Envato نفسها، ولم أرَ ترخيصك أنت.)
- **قبل أي قرار نهائي:** اقرأ ترخيص النسخة التي اشتريتها، أو اسأل 6amTech/Envato كتابةً عن الاستخدام كـ SaaS متعدد المستأجرين.

## 2. خيارات القاعدة المفتوحة المصدر

| الخيار | ما تحقق منه | ما لم يُتحقق منه |
|---|---|---|
| **Bagisto** (Laravel) | النواة بترخيص MIT حسب إعلان في AWS Marketplace | وحدات البائعين المتعددين والـ SaaS تُباع كإضافات مدفوعة (مثلًا إضافة البائعين المتعددين من Webkul بحوالي 449 دولارًا)؛ أرقام الأسعار وشروط إعادة التوزيع تحتاج تأكيدًا من Webkul |
| **Lunar** (Laravel + Filament) | MIT، "headless": خلفية ولوحة إدارة بلا واجهة متجر جاهزة | لا دليل على دعم multi-tenancy مدمج؛ إصدار 1.3.0 يناير 2026 حسب موقع دليل، والتوافق يحتاج مراجعة المستودع الرسمي |
| إضافات التعدد في Bagisto (مدفوعة) | موجودة | شروط ترخيصها لبيعها كخدمة |

**ملاحظة عن الدقة:** مصادر هذا الجدول صفحات تسويقية وأدلة تجميعية. لا أعتبرها نهائية.

## 3. التوصية: مرحلة اختبار قصيرة (Spike) قبل الالتزام

أسبوع واحد لتجربة **Bagisto** و**Lunar** كلٌّ على حدة مع `stancl/tenancy` (قاعدة بيانات لكل تاجر، ترخيص MIT حسب علمي). نقيس:

| المعيار | مطلوب |
|---|---|
| إنشاء مستأجر جديد آليًا (قاعدة + migrations + متجر) | < 60 ثانية، بأمر واحد |
| ترخيص كل مكوّن المستخدم | يسمح بالبيع كخدمة، موثق في LICENSE |
| إمكانيات المتجر مقابل قائمة 6Valley (§4) | تغطية الأساسيات من دون إضافات مدفوعة |
| كلفة إضافة وحدة Affiliate مستقلة | وحدة مستقلة دون تعديل نواة المتجر |
| الأداء مع 50 مستأجرًا تجريبيًا | وقت استجابة مقبول |

**المخرج:** وثيقة قرار قصيرة: القاعدة المختارة + سبب + كلفة الإضافات المدفوعة إن وجدت.
**الميل الأولي (قابل للتغيير بعد الـ Spike):** Lunar مع Filament لأن لوحاتنا الإدارية أصلًا Filament، وبناء واجهة المتجر بأنفسنا. أو Bagisto إذا كانت سرعة الحصول على متجر جاهز أهم من توحيد التقنيات.

## 4. إمكانيات المتجر المطلوبة (مقارنة بـ 6Valley)

| الفئة | MVP للمستأجر | لاحقًا |
|---|---|---|
| كتالوج | منتجات، متغيرات، فئات، علامات، صور، SEO | منتجات رقمية، حزم |
| تسوق | سلة، دفع، كوبونات، عروض فلاش، قائمة أمنيات | مقارنة، مراجعات |
| دفع | COD، بوابات محلية (تحقق من المزوّدين)، محفظة العميل | تقسيط |
| شحن | مناطق وأسعار، تكامل شركات الشحن | تتبع للعميل |
| عملاء | حسابات، عناوين، OTP، ولاء | إحالة |
| بائعون متعددون | تأجيل (Phase 3) | سوق متعدد البائعين |
| ثيمات | ثيم واحد قابل للتخصيص + RTL | سوق ثيمات |
| تطبيقات | PWA | تطبيقات أصلية |
| لغات/عملات | عربي + إنجليزي، EGP | إضافات |
| إدارة | لوحة التاجر (Filament) | صلاحيات متقدمة |
| SaaS | خطط واشتراكات، دومين مخصص، حدود لكل خطة | White-label |

## 5. أثر القرار على الوثائق السابقة

| الوثيقة | التغيير |
|---|---|
| 01 المنتج | "المسوّق" = أفلييت التاجر. شبكة السوق متعددة التجار (نمط تاجر) تصبح اختيارًا لاحقًا لا نواة |
| 02 المعمارية | يضاف: Multi-tenancy (قاعدة لكل تاجر)، قاعدة متجر مفتوحة المصدر، إدارة اشتراكات. الدفتر وآلة الحالات والتسعير تبقى كما هي لكن **داخل كل مستأجر** |
| 03 المخطط | جداول المنصة (tenants، plans، subscriptions، domains) في قاعدة مركزية؛ باقي الجداول لكل مستأجر |
| 07 الخطة | تضاف مجموعتان: `TEN-*` (المستأجرون) و`SAAS-*` (الخطط والفوترة). وتُستبدل `CAT-*` بتكامل مع كتالوج القاعدة المختارة. الكول سنتر والشحن والتسوية والمخزون الذكي تصبح **وحدات اختيارية** تُفعَّل بحسب الخطة |
| 06 المخاطر | يضاف: عزل البيانات بين التجار، قانونية SaaS، دعم عدة تجار، تكلفة التشغيل لكل مستأجر |

## 6. المهام الجديدة (تُضاف إلى 07)

### SPIKE — اختبار القاعدة (أسبوع)
| ID | المهمة |
|---|---|
| SPIKE-01 | تثبيت Bagisto + `stancl/tenancy`، إنشاء 3 مستأجرين، قياس المعايير في §3 |
| SPIKE-02 | تثبيت Lunar + Filament + `stancl/tenancy`، نفس القياس |
| SPIKE-03 | وحدة أفلييت تجريبية (مسوّق، رابط، طلب، عمولة) على كل قاعدة لقياس صعوبة التكامل |
| SPIKE-04 | مراجعة التراخيص وكلفة الإضافات، وكتابة قرار ADR-009 |

### TEN — المستأجرون
| ID | المهمة | معيار القبول |
|---|---|---|
| TEN-01 | نموذج Tenant ودومينات (فرعي ومخصص) وتسجيل التاجر الذاتي | تاجر جديد يحصل على متجر خلال دقيقة |
| TEN-02 | تهيئة المستأجر (migrations، seeders، إعدادات افتراضية، مستخدم مالك) كـ Job | قابل لإعادة التشغيل بدون تكرار |
| TEN-03 | عزل كامل: ملفات، كاش، طوابير، جلسات، سجلات لكل مستأجر | اختبار يثبت عدم قراءة بيانات مستأجر آخر |
| TEN-04 | ترحيل جماعي (`tenants:migrate`) مع تقرير فشل لكل مستأجر | ترحيل 50 مستأجرًا تجريبيًا |
| TEN-05 | لوحة مدير المنصة (Central Admin) | إيقاف/تفعيل مستأجر، دخول كمستأجر مسجَّل في Audit |
| TEN-06 | نسخ احتياطي واستعادة لمستأجر واحد | استعادة تاجر دون المساس بغيره |

### SAAS — الخطط والفوترة
| ID | المهمة | معيار القبول |
|---|---|---|
| SAAS-01 | الخطط والميزات والحدود (منتجات، طلبات، أفلييتات، موظفون) | الحد يُفرض في الخدمات لا في الواجهة فقط |
| SAAS-02 | الاشتراك والفوترة والتجديد وفترة تجريبية | حالات: trial، active، past_due، cancelled |
| SAAS-03 | بوابة دفع الاشتراكات (تحقق من مزوّد يدعم مصر) | |
| SAAS-04 | Feature flags لكل مستأجر (كول سنتر، شحن، مخزون…) | |
| SAAS-05 | إشعارات الاستهلاك والإيقاف المؤقت لعدم الدفع | التاجر لا يفقد بياناته |

## 7. أثر على الجدول الزمني

وجود متجر كامل ومتعدد المستأجرين يطيل الخطة. تقدير أولي (يُراجع بعد الـ Spike):

| المرحلة | الزمن |
|---|---|
| Phase 0 + SPIKE | 3 أسابيع |
| P1: مستأجرون + متجر أساسي + أفلييت (طلب، دفتر، سحب) | 12–14 أسبوعًا |
| P2: وحدات التشغيل الاختيارية (مخزون، شحن، تسوية) | 8 أسابيع |
| P3: SaaS كامل (فوترة، ثيمات، دومين مخصص) + نمو | 8–10 أسابيع |

> تقدير غير مدعوم ببيانات؛ مجرد ترتيب حجم يعتمد على سرعة تكامل القاعدة المختارة.

## 8. قرارات مفتوحة

1. الاعتماد على Bagisto أم Lunar (يُحسم بعد الـ Spike).
2. هل يوجد مصدر دخل من عمولة على مبيعات التجار، أم اشتراك فقط؟
3. بوابات دفع الاشتراك المتاحة لك في مصر.
4. هل نبقي رؤية "شبكة السوق" (نمط تاجر) للمرحلة الأخيرة؟
