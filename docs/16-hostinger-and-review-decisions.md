# 16 — قرارات الاستضافة على Hostinger ومراجعة الخطة (ADR-011)

## 1. الاستضافة المتاحة

من حساب Hostinger (عبر الـ API، 2026-10-26): خطتان نشطتان، **`hostinger_business`** و`hostinger_starter_v2`، وكلتاهما **استضافة مشتركة**. لا يظهر VPS في الحساب.

### قيود الاستضافة المشتركة على معماريتنا

| ما افترضته الخطة | الواقع على الاستضافة المشتركة | القرار |
|---|---|---|
| Docker في الإنتاج | غير متاح | Docker **للتطوير المحلي فقط**؛ الإنتاج PHP مباشرة عبر Git + SSH |
| قاعدة بيانات لكل تاجر (stancl DB-per-tenant) | التطبيق لا يستطيع إنشاء قواعد بيانات بنفسه، وعدد القواعد محدود بالخطة | **قاعدة بيانات واحدة مع عزل بـ `tenant_id`** (single-database tenancy) |
| Redis + Horizon + Supervisor | لا عمليات دائمة (long-running) | طوابير `database` تُشغَّل بـ cron كل دقيقة (`queue:work --stop-when-empty --max-time=50`)، وكاش `database`/`file` |
| SSL آلي لدومين كل تاجر | إضافة الدومينات وشهاداتها تتم عبر hPanel أو API Hostinger، وعددها محدود بالخطة | **MVP بالنطاقات الفرعية** (`store.platform.com`). الدومين المخصص لاحقًا عبر Hostinger API أو بعد الانتقال إلى VPS |
| مهام مجدولة متكررة | cron متاح | `schedule:run` كل دقيقة |

> **يجب التحقق** من حدود خطة Business الحالية (عدد قواعد البيانات، الـ inodes، الـ cron، دعم النطاقات الفرعية wildcard، نسخة PHP 8.3، SSH و Composer) من hPanel. لم أتحقق من هذه الأرقام.

### مبدأ: قابلية النقل
نكتب الكود بحيث **يعمل على الاستضافة المشتركة اليوم، وينتقل إلى VPS لاحقًا بتغيير ملف `.env` فقط** (QUEUE_CONNECTION=redis، CACHE_STORE=redis، إلخ). لا شيء في الكود يعتمد على Redis أو Docker.

### متى ننتقل إلى VPS
عند أي واحد من: أكثر من ~50 تاجرًا نشطًا، أو طوابير تتأخر أكثر من دقيقتين، أو حاجة للدومينات المخصصة على نطاق واسع، أو استهلاك موارد يوقفه Hostinger. Hostinger يقدّم VPS، والنقل يكون بدون تغيير كود.

## 2. أثر قاعدة البيانات الواحدة على Lunar

جداول Lunar لا تحتوي على `tenant_id`. الحل المقترح (يُختبر في P01):
1. Migration من عندنا تضيف `tenant_id` لكل جداول Lunar.
2. استبدال نماذج Lunar بنماذج ترثها وتضيف Global Scope للمستأجر (Lunar يدعم استبدال النماذج عبر ModelManifest — يجب التحقق).
3. اختبار عزل يمر على **كل** نماذج Lunar ونماذجنا.

إن لم ينجح هذا بلا تعديل vendor، فهو معيار فشل في P01 ⇒ البناء من الصفر.

## 3. تقييم المراجعة الخارجية (مراجعة ملصقة من أداة أخرى)

| ملاحظة المراجعة | تقييمي | القرار |
|---|---|---|
| تعارض "شبكة أفلييت تنافس تاجر" مع "SaaS لكل تاجر": المسوّق لن يسجل في 10 متاجر | **صحيحة** | نبقي SaaS (قرار المالك) ونضيف **"الشبكة المركزية" كمرحلة لاحقة**: التاجر يشارك منتجاته بضغطة في كتالوج مشترك، والمسوّق بحساب ومحفظة واحدة. قاعدة البيانات الواحدة تسهّل هذا لاحقًا. القرار النهائي للمالك |
| DB-per-tenant عبء تشغيلي | **صحيحة**، وتحسمها الاستضافة المشتركة | قاعدة واحدة بـ `tenant_id` (أعلاه) |
| فجوة رأس المال العامل: شركات الشحن تسوي بعد أسابيع | **صحيحة**؛ هدف "النافذة + 24 ساعة" في 04 متفائل | إعداد لكل تاجر: `release_mode = return_window \| courier_remittance \| later_of_both`، الافتراضي `later_of_both`. "دفع مبكر برسم" خيار لاحق. في نموذج SaaS، التاجر هو من يدفع لأفلييتاته، ونحن نوفر الأداة |
| تضخم نطاق الـ MVP | **صحيحة** | تحديد MVP صريح (§4) |
