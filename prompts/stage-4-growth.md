# المرحلة 4 — النمو وإكمال الـ SaaS (P28–P33)

## P28 — الدومين المخصص والثيمات

```text
المطلوب (Feature flag: custom_domain):
1. ربط دومين التاجر: إدخال الدومين، تعليمات DNS، التحقق التلقائي، إصدار SSL آلي (ابحث عن الطريقة الأنسب لبنيتنا: Caddy on-demand TLS أو Traefik + Let's Encrypt، ووثّق القرار)، وإعادة التوجيه من النطاق الفرعي.
2. تخصيص الثيم المتقدم: أقسام الصفحة الرئيسية بالسحب والإفلات، صفحات مخصصة، قوائم، تذييل.
3. ثيم ثانٍ على الأقل (هيكل ثيمات قابل للتوسع).
4. White-label للخطط العليا: إخفاء اسم المنصة.

معايير القبول: اختبار تحديد المستأجر بالدومين المخصص، وسيناريو SSL موثق على staging.

الخاتمة: فرع feat/SAAS-domains-themes، PR.
```

## P29 — API العام و Webhooks

```text
المطلوب (Feature flag: api):
1. REST API v1 للتاجر (المنتجات، الطلبات، المخزون، العملاء) وللأفلييت (الكتالوج، إنشاء طلب، حالة الطلبات، المحفظة).
2. مفاتيح API بنطاقات (scopes)، Rate limits حسب الخطة، Idempotency-Key إلزامي في الإنشاء.
3. توثيق OpenAPI تلقائي (Scramble أو مكافئ) وصفحة توثيق عامة.
4. Webhooks صادرة موقّعة (HMAC) لأحداث الطلب والمخزون والسحب، مع إعادة محاولة تصاعدية وسجل تسليم.
5. نموذج طلب قابل للتضمين (embed) لصفحات هبوط الأفلييت مع UTM.

معايير القبول: اختبارات العقد (contract) للـ API، والتحقق من التوقيع، وإعادة المحاولة.

الخاتمة: فرع feat/GRW-api، PR.
```

## P30 — التتبع الإعلاني (Pixel و Conversions API)

```text
المطلوب:
1. إعداد Meta Pixel و TikTok Pixel للمتجر وللأفلييت (كلٌّ ببكسله).
2. أحداث المتجر في المتصفح: ViewContent، AddToCart، InitiateCheckout، Purchase.
3. Conversions API من السيرفر مع event_id لمنع التكرار، وبيانات مجزأة (hash) حسب متطلبات كل منصة — تحقق من الوثائق الرسمية الحالية.
4. حدث مخصص عند **التسليم الفعلي** لتحسين الحملات على الطلبات الحقيقية لا المرفوضة.
5. لوحة تشخيص: آخر الأحداث المرسلة وحالتها.

معايير القبول: اختبارات بـ Fake HTTP، واختبار event_id ثابت بين المتصفح والسيرفر.

الخاتمة: فرع feat/GRW-pixels، PR.
```

## P31 — أدوات الذكاء الاصطناعي

```text
اقرأ: وثائق Claude API الحالية (استخدم أحدث نموذج مناسب).

المطلوب (Feature flag: ai):
1. AIProvider interface + تنفيذ Claude، المفتاح على مستوى المنصة، مع حد استخدام شهري حسب الخطة وعداد.
2. للتاجر: توليد وصف المنتج و SEO بالعربية الفصحى/العامية المصرية والإنجليزية، اقتراح فئات ووسوم، ترجمة.
3. للأفلييت: نصوص إعلانات (فيسبوك/تيك توك) بعدة نبرات، أفكار زوايا تسويق، فحص نص الإعلان من الوعود المبالغ فيها.
4. سجل الاستخدام والتكلفة لكل مستأجر.
5. لا تُرسل بيانات العملاء الشخصية للنموذج.

معايير القبول: اختبارات بـ Fake provider، واختبار الحد الشهري.

الخاتمة: فرع feat/GRW-ai، PR.
```

## P32 — الدعم والتذاكر

```text
المطلوب:
1. تذاكر على مستويين: (أ) أفلييت/عميل ⇒ التاجر، (ب) التاجر ⇒ المنصة.
2. ربط التذكرة بطلب/سحب، أولوية، SLA بموعد استحقاق، تعيين، ملاحظات داخلية، مرفقات.

4. مركز مساعدة/أسئلة شائعة لكل متجر وللمنصة.

معايير القبول: اختبارات SLA بـ travelTo والصلاحيات.

الخاتمة: فرع feat/GRW-support، PR.
```

## P33 — التقارير والتحليلات

```text
المطلوب:
1. للتاجر: المبيعات، الأرباح، أفضل المنتجات، الأفلييتات، المحافظات، المرتجعات وأسبابها، المخزون، الضرائب. فلترة بالتاريخ وتصدير CSV/Excel.
2. للمنصة: التجار النشطون، MRR، Churn، الاستخدام لكل خطة، الأخطاء لكل مستأجر.
3. جداول تجميع يومية (لا استعلامات ثقيلة على البيانات الحية)، مع اختبار يقارن التجميع بالعدّ المباشر.
4. لوحة "المؤشرات العلنية" اختيارية لكل متجر (زمن الدفع، نسبة التسليم) يعرضها في صفحة الأفلييت.

معايير القبول: تطابق التجميع مع العد المباشر في الاختبارات.

الخاتمة: فرع feat/GRW-reports، PR.
```
