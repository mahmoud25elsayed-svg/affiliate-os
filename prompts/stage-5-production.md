# المرحلة 5 — الإنتاج والإطلاق (P34–P40)

---

## P34 — مراجعة أمنية شاملة

```text
أنت مراجع أمني. اقرأ CLAUDE.md و docs/02 §8.

المطلوب:
1. راجع الكود كله مقابل OWASP Top 10 وأعد تقريرًا في docs/security/review-<date>.md بالأولوية.
2. ركّز على: عزل المستأجرين (أي استعلام أو Job أو كاش يتسرب بين التجار)، IDOR في كل endpoint يأخذ id، رفع الملفات، SSRF في Webhooks والدومينات، صلاحيات Filament، تشفير الحقول الحساسة، الأسرار في السجلات.
3. اكتب اختبارًا فاشلًا لكل ثغرة قبل إصلاحها، ثم أصلحها.
4. أضف أدوات فحص إلى CI: composer audit، npm audit، فحص أسرار (gitleaks أو مكافئ).
5. سياسة كلمات المرور، 2FA، انتهاء الجلسات، رؤوس الأمان (CSP، HSTS…).

معايير القبول: لا ثغرة حرجة/عالية مفتوحة. اختبار عزل شامل يمر على كل Model في المستأجر.

الخاتمة: فرع sec/review، PR.
```

## P35 — الأداء واختبار الحمل

```text
المطلوب:
1. سيناريوهات k6: تصفح المتجر، checkout، إنشاء طلب أفلييت (50 طلب/ثانية)، 20 موظف كول سنتر متزامن، Webhooks الشحن.
2. 200 مستأجر تجريبي على staging.
3. حدد الاختناقات (Telescope/slow query log)، أضف فهارس، كاش، تقسيم الطوابير (finance، notifications، courier، default) بأولويات.
4. هدف: p95 < 500ms للصفحات العامة، لا deadlocks غير معالجة، لا طوابير عالقة.

معايير القبول: تقرير قبل/بعد في docs/perf/.

الخاتمة: فرع perf/load، PR.
```

## P36 — البنية والنشر والنسخ الاحتياطي

```text
المطلوب:
1. اقترح بنية الإنتاج (VPS واحد ثم توسع) بتكلفة تقريبية، ووثّق في docs/15-infrastructure.md. انتظر موافقتي قبل إنشاء أي مورد مدفوع.
2. Docker للإنتاج، reverse proxy مع SSL آلي للدومينات المخصصة، مستخدم غير root، جدار ناري.
3. GitHub Actions: نشر staging عند الدمج في main، ونشر production عند tag، مع migrations للمركزي ثم tenants:migrate، ووضع صيانة قصير، وتراجع (rollback).
4. نسخ احتياطي يومي للقاعدة المركزية وكل مستأجر والملفات خارج الخادم، مع **اختبار استعادة آلي شهري**.
5. مراقبة: Uptime، Horizon، القرص، الذاكرة، فشل ledger:reconcile، فشل provisioning ⇒ تنبيهات.
6. الأسرار في متغيرات البيئة على الخادم فقط، وتوثيق تدويرها.

معايير القبول: نشر كامل لـ staging من الصفر بأمر/workflow واحد، واستعادة نسخة احتياطية لمستأجر واحد موثقة.

الخاتمة: فرع ops/infra، PR.
```

## P37 — الامتثال والصفحات القانونية

```text
المطلوب:
1. قوالب (مسودات للمراجعة القانونية، لا نصوص نهائية): شروط المنصة للتجار، اتفاقية معالجة البيانات بين المنصة والتاجر، شروط برنامج الأفلييت، الخصوصية، الشحن والمرتجع، سياسة الاستخدام المقبول.
2. أدوات: تصدير بيانات عميل، حذف/إخفاء بيانات، سجل الموافقات، سياسة الاحتفاظ بالبيانات (حذف آلي للنقرات والسجلات القديمة).
3. ضع تنبيهًا صريحًا في كل قالب: "يتطلب مراجعة محامٍ قبل النشر" (قانون حماية البيانات الشخصية المصري 151 لسنة 2020 وحماية المستهلك).

الخاتمة: فرع legal/templates، PR.
```

## P38 — صفحة التسويق للمنصة والتسعير والتجربة الأولى

```text
المطلوب:
1. موقع المنصة: الرئيسية، الميزات، الأسعار (من جدول plans)، مقارنة الخطط، الأسئلة الشائعة، المدونة، تواصل. SEO كامل بالعربية.
2. Onboarding موجّه للتاجر الجديد: قائمة خطوات (الشعار، أول منتج، الشحن، الدفع، تفعيل الأفلييت) مع نسبة إنجاز.
3. بيانات تجريبية اختيارية بزر واحد لمتجر جديد وحذفها بزر.
4. تحليلات المنصة للزوار والتحويل (أداة تحترم الخصوصية).

الخاتمة: فرع feat/SAAS-marketing، PR.
```

## P39 — جاهزية الإطلاق

```text
المطلوب — قائمة تحقق تُنفذ وتُوثَّق في docs/launch-checklist.md:
1. كل الاختبارات خضراء، لا ثغرات مفتوحة، تقرير الأداء مقبول.
2. Seed الإنتاج: الخطط، المحافظات، الإعدادات، حساب مدير المنصة بـ 2FA.
3. نسخة احتياطية مستعادة بنجاح خلال الأسبوع.
4. المراقبة والتنبيهات مجربة.
5. الصفحات القانونية مراجعة من محامٍ (أؤكد ذلك أنا يدويًا).
6. Runbooks للحوادث: توقف قاعدة، فشل بوابة دفع، فرق في الدفتر، تسريب بيانات.
7. خطة أول أسبوعين: مراقبة يومية، قناة دعم مباشرة، مراجعة المؤشرات.

الخاتمة: tag v1.0.0 بعد موافقتي فقط.
```
